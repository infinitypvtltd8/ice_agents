# Rule implementation and verification map

The latest user-provided extraction and XML tagging guide is `LATEST_RULES.txt`; consult it alongside `SOURCE_REQUIREMENTS.txt` and `MASTER_RULE_ENGINE_SPECIFICATION.md`. The JSON catalogue contains 123 numbered contracts across references (22), affiliations (18), contacts (11), XML (11), extraction (8), metadata (8), authors (8), review (8), ingestion (6), identity (6), runtime (4), validation (4), export (4), batch (3), and testing (2). At this audit baseline, all 123 catalogue entries still say `SPECIFIED_NOT_IMPLEMENTED`; that is a conservative catalogue state, not a claim that the app has no related behavior. The application also has a separate configurable rulebook with 17 runtime checks. The rule catalogue and that runtime rulebook are not yet connected by a complete handler/test traceability map. Prose files are not dynamically interpreted by the runtime. Runtime findings are review notes: ICE has no HOLD state, and findings do not block XML generation, metadata saving or export.

Keep reference source transcriptions faithful to the PDF. Do not enrich outside the supplied package. A green check means the rule found nothing, not that every visual nuance was understood. Review notes can coexist with XML output and export.

The initial XML is generated in the same automatic job that assigns the queue. Support XML/HTML text and attribute values are persisted in JSON/Markdown feeders; current metadata and XML have inspectable mirrors in each job directory. The demo now includes an explicitly synthetic General case alongside three complex research examples.

## Numbered rule lifecycle

1. Locate the ID in `config/specification_rules.json` and the full contract in `MASTER_RULE_ENGINE_SPECIFICATION.md`.
2. Define primary and secondary sources, precedence, exact failure severity, issue text, and coordinate evidence.
3. Implement a deterministic handler in the correct stage; keep unresolved cases in review, not guessed output.
4. Add a representative test with a positive and discrepancy case, ideally including source files and XML mapping.
5. Update the rule's implementation status only after end-to-end evidence is available. Record limits here.

## Full-catalogue audit baseline (2026-10-30)

The full rule set is already present in this project; it does not need to be resent. This baseline deliberately does not promote catalogue entries based on keyword matches alone. Each rule needs a concrete handler path, evidence behavior, and a positive plus discrepancy test before its catalogue status can change. Existing targeted regressions cover selected identity, title, author, affiliation, abstract, keyword, reference, XML, and nonblocking-review behaviors; they do not establish that every contract above is complete. The full test suite currently has two failing app regressions: one sample's abstract is empty, and one sample's routing findings differ from the older expected set. Treat those as unresolved audit items rather than changing expected values to force a pass. The remaining 121-rule traceability and behavior audit is still required.

## Text fidelity additions (2026-10-30)

- Preserve the PDF's English abstract wording and Unicode diacritics. Normalize to NFC and repair only known, unambiguous accent-glyph artifacts; never remove accents or transliterate names. Keep original source evidence and emit a nonblocking issue when U+FFFD remains.
- Emit `<sup>` or `<inf>` only when PDF glyph geometry/style identifies raised or lowered text and the glyph sequence can be mapped exactly to the extracted plain text. If mapping is uncertain, retain the plain text and leave a review note; do not guess at a character or position.
- Use `(Formula presented)` only for a self-contained, symbol-dense display equation whose layout cannot be represented as linear text without changing its meaning. Preserve all surrounding abstract prose. Never replace ordinary inline math or prose based on symbols alone. Keep PDF region evidence for every replacement.
- Retain every extracted abstract and keyword character in XML text. XML serialization must preserve Unicode and escape XML syntax; HTML entities are not a substitute for the original characters.
- The two identity rules in the `Special cases` UI compare the PDF stamp with Scrapping/HTML evidence. Findings are informational and must never prevent save or export. A clean check is not proof of complete extraction; reviewers can edit all metadata and XML fields.
- A passed parser/profile check does not establish XSD validity unless the exact delivery XSD is supplied. Do not describe any extraction run as 100% accurate; verify representative PDF/XML pairs and report unresolved cases.
- Treat the full heading `Key words and phrases` as a label; do not emit the words `and phrases` as an author keyword.
- For Dutch addresses, recognize the full `NNNN AA` postcode, preserve it as one postal-code value, classify city names separately, and recognize local street suffixes such as `-weg`. Keep company names such as Thermo Fisher Scientific in organization, never address-part.
- Before emitting affiliation groups, check for a repeated author group whose source text and organization are only a strict trailing fragment of an otherwise complete affiliation with the same locality/postcode/country. Retain the complete affiliation and evidence; do not output the fragment as an additional group. Keep any case that does not satisfy all those checks for review.
- Escape XML text characters (`&`, `<`, `>`) during serialization so references and organization names remain parseable without changing their displayed text.

No external schema was provided. Official XSD validation remains a separate integration task. The sample-profile checker must not be relabeled as an official pass.
